## Готовые ответы на вопросы, которые уже поднимались

### ✅ Можно ли через `commands/route` перевести звонок на произвольный внешний мобильный?

**Да, официально.** Раздел 3.2.7, стр. 46, дословно:

> «если параметр `to_number` является номером в формате sip, fmc, **pstn** - команда будет
> инициировать **безусловное перенаправление звонка на этот номер без каких-либо иных условий**»

Это закрывает главный вопрос по фиче «админ звонит сам, без интернета». Поддержка Mango
на письмо про это не ответила за месяц - ответ всё это время был в доке.

### ✅ Нужна ли платная услуга «API: Webhooks» (2100 ₽/мес) для приёма `events/call`?

**Нет.** Методичка «Вебхуки» описывает ровно три сценария, и все - в направлении
«внешняя система дёргает Mango по HTTP-ссылке»: `Action=Send_SMS`, `Action=Callback`,
`Action=CC_Add` (добавить контакт в обзвон). Приём событий там не упоминается вообще.

Приём `events/call` - это **«API Realtime», раздел 3.1 базового API ВАТС**, работает
через обычный API коннектор (у заказчика уже активен и оплачен).

### ❓ Какой номер увидит вызываемый абонент при `route`?

**Прямого ответа в доке нет** - это реальный пробел, а не недосмотр поиска.
Что известно точно:

- у `route` **нет** параметра подмены АОН (в отличие от `callback` с `line_number`);
- единственное, что можно подменить - **отображаемое имя** через
  `sip_headers` → `From/display-name` (Приложение 1, стр. 349), не номер;
- в примере доки (стр. 337) после `route` в новом вызове **сохраняется `line_number`** -
  номер линии, на которую поступил исходный звонок. Косвенный аргумент за то, что
  покажется служебный номер, а не мобильный сотрудника. Но это вывод, не цитата.

Проверять живым тестом.

## Требования к нашему серверу (разделы 1.2, 1.3, 3.1.1)

| Требование | Значение | Статус |
|---|---|---|
| Протокол | HTTPS, **TLS строго 1.2** | ✅ Caddy, проверено `--tls-max 1.2` → 200 |
| TLS 1.0 / 1.1 / **1.3** | **НЕ поддерживаются Mango** | учтено |
| Методы | POST и GET | ✅ |
| IP-адреса Mango (whitelist) | `81.88.80.132`, `81.88.80.133`, `81.88.82.36`, `81.88.82.44`, `81.88.82.45` | ✅ все 5 в Caddy |

⚠️ **Про IP:** их **пять**, а не три. В сторонних мануалах и старых версиях доки фигурируют
только первые три - с таким списком часть событий молча резалась бы в 403.

### Как Mango формирует URL событий

В личном кабинете указывается **только базовый адрес**, путь система достраивает сама
(раздел 2.2, стр. 12). Пример из доки: база `https://external-system.com/mango-api-connector/`
→ события летят на `https://external-system.com/events/call`.

Наш базовый адрес: `https://call-masking.duckdns.org/webhooks/mango/`
→ значит эндпоинты в коде должны быть `/webhooks/mango/events/call`, `/events/dtmf` и т.д.

### Подпись запроса (раздел 2.4, стр. 14-15)

```
sign = sha256(vpbx_api_key + json + vpbx_api_salt)
```

- JSON-строка - **без лишних пробелов и переносов**, и в подписи, и в поле формы должна
  быть **одна и та же строка** (иначе подпись не сойдётся). У нас это учтено в
  `app/services/mango.py`.
- **Подписываются все запросы, в обе стороны** - включая те, что Mango шлёт нам.
  То есть входящие события можно и нужно верифицировать по подписи.

### Лимиты (раздел 1.4)

| Что | Лимит |
|---|---|
| **Неверные запросы** | **1 в 2 минуты**, дальше HTTP 401 и блокировка доступа на 2 мин |
| `commands/route` | 1 запрос / 2 сек по продукту, 10/сек суммарно |
| `commands/callback` | 4/сек по продукту, 10/сек суммарно |
| `call/hangup` | 4/сек по продукту |
| `config/users/request` | 1 запрос / 2 сек |
| Превышение | HTTP 429 `Rate limit exceeded` |

⚠️ Лимит на **неверные** запросы жёсткий - при отладке нельзя долбить API кривыми
payload'ами, доступ отрубится.

## Подводные камни (проверено / вычитано)

1. **`events/call` приходит НЕ всегда.** Стр. 21: если вызов пришёл в нерабочее время по
   расписанию абонента - уведомление **не отправляется**. Исключение - статус «не беспокоить»
   в КЦ: там событие придёт. Для служебного номера расписание должно быть круглосуточным.

2. **События приходят не по порядку.** Есть счётчик `seq` - уведомления шлются параллельно.
   Обрабатывать по `seq`, событие с меньшим номером игнорировать (стр. 19).

3. **`result` = 1000 - это успех, а не ошибка.** Классика граблей: у нас в
   `app/services/mango.py` успехом считаются `0` и `1000`.

4. **Коды HTTP в доке описаны нелогично** (стр. 12): класс `2xx` там значится как
   «передан неверный запрос». Ориентироваться на `result` в теле, а не только на HTTP-код.

5. **`route` работает не в любой момент.** Только пока вызов в IVR / очереди, либо
   распределён на сотрудника, но **трубку ещё не сняли** (состояние `Appeared`).
   После `Connected` - уже `transfer`, а не `route`.

6. **Для `callback` `line_number` обязателен** - иначе Mango подставит личный номер
   сотрудника и маскировка сломается. У нас это защищено исключением в коде.

7. **`sip_headers` меняет только ИМЯ, не номер.** `From/display-name` - до 64 байт.

8. **Автоответ:** `sip_headers` → `Call-Info/answer-after: "0"` в `callback` заставляет
   принять вызов без снятия трубки. Может пригодиться для сценария без интернета.

## Заготовки на будущее

- **Как узнать свободный номер из 56, не дёргая заказчика:** `POST /vpbx/incominglines`
  (стр. 122) отдаёт все номера ВАТС с `line_id`, `number`, `schema_id` и **названием схемы
  распределения**. Можно программно увидеть, какой номер на какой схеме висит.
- **Как сверить `extension` сотрудников:** `POST /vpbx/config/users/request` (стр. 105).
  Именно этим методом чинили баг с чужим extension.
- **Если понадобится DTMF-выбор заявки** (у админа несколько одобренных): готовый рецепт
  настройки IVR-схемы с блоком донабора (DISA) на 1-99 цифр + сообщение «ожидайте» с
  паузой, пока наш сервер думает - стр. 345-346.
