## Готовые ответы на вопросы, которые уже поднимались

### ✅ Можно ли через `commands/route` перевести звонок на произвольный внешний мобильный?

**Да, официально.** Раздел 3.2.7, стр. 46, дословно:

> «если параметр `to_number` является номером в формате sip, fmc, **pstn** - команда будет
> инициировать **безусловное перенаправление звонка на этот номер без каких-либо иных условий**»

Это закрывает главный вопрос по фиче «админ звонит сам, без интернета». Поддержка Mango
на письмо про это не ответила за месяц - ответ всё это время был в доке.

### ✅ Нужна ли платная услуга «API: Webhooks» (2100 ₽/мес) для приёма `events/call`?

**Нет, это не она.** Методичка «Вебхуки» описывает ровно три сценария, и все - в
направлении «внешняя система дёргает Mango по HTTP-ссылке»: `Action=Send_SMS`,
`Action=Callback`, `Action=CC_Add`. Приём событий там не упоминается вообще.
Приём `events/call` - это «API Realtime», раздел 3.1 базового API ВАТС.

⚠️ **Но это НЕ значит, что события придут бесплатно** - см. следующий пункт.

### ⛔ Почему `events/call` и `result/callback` к нам не приходят (проверено 30.07.2026)

**Факт, а не догадка.** За 48 часов в логах Caddy на проде - **ноль** запросов с IP
Mango, при том что в тот же период прошло 6 успешных боевых `commands/callback`
(`result: 1000`). Единственная запись про `events/call` в логах бота - наш собственный
тестовый curl.

**Причина:** в ЛК не задан **базовый адрес внешней системы**. Без него ВАТС физически
некуда слать ни события, ни отчёты о результате команд.

**Побочное следствие, которое легко проглядеть:** по этой же причине никогда не работал
`POST /webhooks/mango/call` - откат заявки в `CALL_APPROVED`, когда клиент не взял
трубку. Код есть и он корректен, но Mango к нему не обращался ни разу.

**Где задаётся адрес.** Раздел 2.2 (стр. 11): «базовый адрес внешней системы должен быть
указан **при подключении API**». Единственное место в ЛК - Интеграции → **API коннектор**
→ кнопка «Подключить API коннектор» (Рисунок 1 в доке, стр. 13 - страница один в один
совпадает с тем, что видно в кабинете заказчика). После подключения страница выглядит
иначе (скриншот на стр. 15): появляется кнопка «Отключить» и блок «Настройки API
коннектора» → «Данные вашей АТС».

⚠️ **Раздел «Мои интеграции» ≠ подключённый API коннектор.** Там показаны те же
`Уникальный код вашей АТС` / `Ключ для создания подписи`, поэтому легко решить, что всё
уже настроено. Но на скриншоте из доки, где коннектор ещё НЕ подключён, в левом меню
тоже висит «Мои интеграции (1)». Ключи выданы под интеграцию amoCRM; для команд
(`callback`, `route`) их хватает, а поля адреса там нет.

### 💰 Про кнопку «Подключить API коннектор» (7700 ₽/мес)

Модалка называет услугу «API: Возможность использовать API-**конструктор**» - по названию
кажется, что это другой продукт, но путь в ЛК и внешний вид страницы **совпадают с
Рисунком 1 официальной доки**, где эта же кнопка описана как активация API коннектора.

Что установлено точно (проверено боевыми ключами с прод-сервера):
- базовые методы API работают **без** активации: `incominglines`, `schemas`,
  `stats/calls/*`, `commands/callback` - все вернули `result: 1000`;
- код `5201` («API коннектор не активирован») по разделу 2.3 возвращается только для
  методов, которые **манипулируют услугами** - мы такие не используем.

То есть активация нужна не ради самих вызовов API, а ради **поля адреса внешней системы**.
Прежде чем платить - запросить у Mango письменное подтверждение: открывает ли эта услуга
приём `events/call` и `result/*` на свой адрес. Решение о деньгах - за заказчиком.

### ❓ Какой номер увидит вызываемый абонент при `route`?

**Прямого ответа в доке нет** - это реальный пробел, а не недосмотр поиска.
Что известно точно:

- у `route` **нет** параметра подмены АОН (в отличие от `callback` с `line_number`);
- единственное, что можно подменить - **отображаемое имя** через
  `sip_headers` → `From/display-name` (Приложение 1, стр. 349), не номер;
- в примере доки (стр. 337) после `route` в новом вызове **сохраняется `line_number`** -
  номер линии, на которую поступил исходный звонок. Косвенный аргумент за то, что
  покажется служебный номер, а не мобильный сотрудника. Но это вывод, не цитата.

Проверять живым тестом.

## Требования к нашему серверу (разделы 1.2, 1.3, 3.1.1)

| Требование | Значение | Статус |
|---|---|---|
| Протокол | HTTPS, **TLS строго 1.2** | ✅ Caddy, проверено `--tls-max 1.2` → 200 |
| TLS 1.0 / 1.1 / **1.3** | **НЕ поддерживаются Mango** | учтено |
| Методы | POST и GET | ✅ |
| IP-адреса Mango (whitelist) | `81.88.80.132`, `81.88.80.133`, `81.88.82.36`, `81.88.82.44`, `81.88.82.45` | ✅ все 5 в Caddy |

⚠️ **Про IP:** их **пять**, а не три. В сторонних мануалах и старых версиях доки фигурируют
только первые три - с таким списком часть событий молча резалась бы в 403.

### Как Mango формирует URL событий

В личном кабинете указывается **только базовый адрес**, путь система достраивает сама
(раздел 2.2, стр. 12). Пример из доки: база `https://external-system.com/mango-api-connector/`
→ события летят на `https://external-system.com/events/call`.

Наш базовый адрес: `https://call-masking.duckdns.org/webhooks/mango/`
→ значит эндпоинты в коде должны быть `/webhooks/mango/events/call`, `/events/dtmf` и т.д.

### Подпись запроса (раздел 2.4, стр. 14-15)

```
sign = sha256(vpbx_api_key + json + vpbx_api_salt)
```

- JSON-строка - **без лишних пробелов и переносов**, и в подписи, и в поле формы должна
  быть **одна и та же строка** (иначе подпись не сойдётся). У нас это учтено в
  `app/services/mango.py`.
- **Подписываются все запросы, в обе стороны** - включая те, что Mango шлёт нам.
  То есть входящие события можно и нужно верифицировать по подписи.

### Лимиты (раздел 1.4)

| Что | Лимит |
|---|---|
| **Неверные запросы** | **1 в 2 минуты**, дальше HTTP 401 и блокировка доступа на 2 мин |
| `commands/route` | 1 запрос / 2 сек по продукту, 10/сек суммарно |
| `commands/callback` | 4/сек по продукту, 10/сек суммарно |
| `call/hangup` | 4/сек по продукту |
| `config/users/request` | 1 запрос / 2 сек |
| Превышение | HTTP 429 `Rate limit exceeded` |

⚠️ Лимит на **неверные** запросы жёсткий - при отладке нельзя долбить API кривыми
payload'ами, доступ отрубится.

## Подводные камни (проверено / вычитано)

1. **`events/call` приходит НЕ всегда.** Стр. 21: если вызов пришёл в нерабочее время по
   расписанию абонента - уведомление **не отправляется**. Исключение - статус «не беспокоить»
   в КЦ: там событие придёт. Для служебного номера расписание должно быть круглосуточным.

2. **События приходят не по порядку.** Есть счётчик `seq` - уведомления шлются параллельно.
   Обрабатывать по `seq`, событие с меньшим номером игнорировать (стр. 19).

3. **`result` = 1000 - это успех, а не ошибка.** Классика граблей: у нас в
   `app/services/mango.py` успехом считаются `0` и `1000`.

4. **Коды HTTP в доке описаны нелогично** (стр. 12): класс `2xx` там значится как
   «передан неверный запрос». Ориентироваться на `result` в теле, а не только на HTTP-код.

5. **`route` работает не в любой момент.** Только пока вызов в IVR / очереди, либо
   распределён на сотрудника, но **трубку ещё не сняли** (состояние `Appeared`).
   После `Connected` - уже `transfer`, а не `route`.

6. **Для `callback` `line_number` обязателен** - иначе Mango подставит личный номер
   сотрудника и маскировка сломается. У нас это защищено исключением в коде.

7. **`sip_headers` меняет только ИМЯ, не номер.** `From/display-name` - до 64 байт.

8. **Автоответ:** `sip_headers` → `Call-Info/answer-after: "0"` в `callback` заставляет
   принять вызов без снятия трубки. Может пригодиться для сценария без интернета.

9. **Даты в статистике - московские, сервер живёт в UTC.** `stats/calls/request` трактует
   `start_date`/`end_date` как МСК. Если слать `datetime.now()` с UTC-сервера, верхняя
   граница окна срезает последние 3 часа, и выглядит это как «статистика отстаёт».
   Перед отправкой добавлять +3 часа.

10. **Служебный номер нельзя оставлять на схеме колл-центра.** `route` работает, только
    пока трубку не сняли (состояние `Appeared`). Если номер висит на общей схеме
    «Распределение на КЦ», вызов уйдёт в очередь к живым операторам, и любой снявший
    трубку переведёт вызов в `Connected` - `route` уже не применим, нужен `transfer`.
    Служебной линии нужна отдельная схема, которая держит вызов (IVR/приветствие).

11. **Расписание схемы должно быть круглосуточным.** Стр. 21: если вызов пришёл в
    нерабочее время абонента, уведомление `events/call` **не отправляется вообще**.
    Выездные админы звонят ночью - это как раз наш случай.

12. **`python-multipart` обязателен** (наши грабли, 29.07.2026). Mango шлёт webhook-и
   form-data. Starlette требует этот пакет для `request.form()` при **любом**
   content-type, включая `urlencoded`. Без него эндпоинт отвечает 200, но payload не
   разбирается - выглядит как «Mango прислал кривой json». Пакет в `requirements.txt`,
   есть тест-страж `test_multipart_dependency_installed`.

## Заготовки на будущее

- **Как узнать свободный номер, не дёргая заказчика** - ✅ проверено 30.07.2026.
  `POST /vpbx/incominglines` (стр. 122, тело `{}`) отдал все номера ВАТС с `line_id`,
  `number`, `schema_id`, `schema_name` и `comment`. Комментарий у заказчика заполнен
  осмысленно (город/площадка) - номера с пустым `comment` и самыми большими `line_id`
  и есть свежекупленные кандидаты. `POST /vpbx/schemas` (стр. 124, тело `{}`) отдаёт
  схемы с массивом привязанных линий - видно, какие схемы стоят пустыми.
  ⚠️ Пустой `comment` - основание **предложить** номер заказчику, но не занять его
  самим: `POST /vpbx/schema/set` (стр. 127) меняет боевую маршрутизацию телефонии клиники.
- **Как сверить `extension` сотрудников:** `POST /vpbx/config/users/request` (стр. 105).
  Именно этим методом чинили баг с чужим extension.
- **Если понадобится DTMF-выбор заявки** (у админа несколько одобренных): готовый рецепт
  настройки IVR-схемы с блоком донабора (DISA) на 1-99 цифр + сообщение «ожидайте» с
  паузой, пока наш сервер думает - стр. 345-346.

### Запасной путь, если приём событий останется недоступен

Если платить за активацию коннектора заказчик не захочет, фичу «звонок без интернета»
всё равно можно сделать - **опросом статистики вместо webhook-ов**. Проверено на боевых
ключах 30.07.2026:

`POST /vpbx/stats/calls/request/` (тело: `start_date`, `end_date`, `limit`, `offset`,
`context_type: 1` - только входящие) отдаёт `key`, затем `POST /vpbx/stats/calls/result/`
с этим `key` возвращает отчёт. Формируется он **за ~2 секунды**, данные свежие: звонок,
завершившийся 11 минут назад, уже был в выборке. Полезные поля записи: `caller_number`,
`called_number`, `context_start_time` (unix), `duration`, `talk_duration`,
`context_status` (1 - разговор состоялся, 0 - нет).

Сценарий: админ звонит на служебный номер и **сбрасывает**, не дожидаясь ответа → опрос
раз в несколько секунд видит входящий с его АОН → бот дёргает уже работающий
`commands/callback` и соединяет админа с клиентом.

Два плюса против плана с `route`: не нужен приём событий вообще, и **маскировка
гарантирована** - у `callback` есть `line_number`, то есть клиент увидит корпоративный
номер (у `route` подмены АОН нет, и это до сих пор открытый вопрос).
Минус - задержка: вместо мгновенного соединения админ ждёт обратного звонка.
